# STEP 01: リークするコードを読もう

## このステップで学ぶこと

このハンズオンでは、ゴールーチンリークを題材にします。
ゴールーチンリークとは、ゴールーチンが何かを待ってブロックしたまま、待っている条件が二度と満たされなくなり、終了できなくなってしまう状態のことです。
リークしたゴールーチンは、ゴールーチン自身が使うメモリや、ゴールーチンが参照しているメモリを抱えたまま残り続けます。
気づかないうちに少しずつ積み重なり、メモリ使用量の増加やGCの負荷の増加につながります。

STEP 01では、リークを起こすコードを読み、実際にゴールーチンが残ってしまうことを確かめます。
その過程で、次のことを学びます。

* ゴールーチンリークが起きる仕組み
* バッファなしチャネルへの送信がブロックする条件
* `runtime.NumGoroutine`関数によるゴールーチン数の確認

## 題材: 最初に返ってきた結果を使う検索

`search`パッケージの`First`関数は、複数のバックエンドに並行して問い合わせ、最初に返ってきた結果を返します。
たとえば、同じ内容を持つ複数のサーバに問い合わせて、いちばん早く答えたサーバの結果を使いたい場合に便利な処理です。

```go
// Backend は検索を行うバックエンドである。
type Backend func(ctx context.Context, query string) (string, error)

type result struct {
	val string
	err error
}

// First はすべてのバックエンドに並行して問い合わせ、
// 最初に返ってきた結果を返す。
func First(ctx context.Context, query string, backends []Backend) (string, error) {
	ch := make(chan result)
	for _, b := range backends {
		go func() {
			v, err := b(ctx, query)
			ch <- result{val: v, err: err}
		}()
	}

	r := <-ch
	return r.val, r.err
}
```

`First`関数は、バックエンドの数だけゴールーチンを起動し、各ゴールーチンはバックエンドの結果をチャネル`ch`に送信します。
呼び出し元のゴールーチンは、`ch`から1回だけ受信して、その結果を返します。

Go 1.22以降では、`for`文の変数がループの繰り返しごとに別の変数になります。
そのため、ゴールーチンの中で`b`をそのまま使っても、すべてのゴールーチンが同じバックエンドを呼び出してしまうことはありません。

## 何が問題なのか

`ch`は`make(chan result)`で作られた、バッファなしのチャネルです。
バッファなしのチャネルへの送信は、受信する側が現れるまでブロックします。

3つのバックエンドがあるとき、`First`関数の中では次のことが起きます。

1. 3つのゴールーチンが起動し、それぞれがバックエンドに問い合わせる
2. いちばん早い結果が`ch`に送信され、`First`関数が受信して戻る
3. 残りの2つのゴールーチンも、遅れて結果を`ch`に送信しようとする
4. しかし`First`関数はもう戻っており、`ch`から受信するゴールーチンは存在しない
5. 残りの2つのゴールーチンは、`ch <- result{val: v, err: err}`でずっとブロックし続ける

このとき、`ch`は`First`関数のローカル変数なので、`First`関数が戻ったあとは、ブロックしているゴールーチン以外から参照されることはありません。
つまり、誰も受信できないチャネルへの送信で待ち続ける、リークしたゴールーチンが2つ残ります。
`First`関数を1回呼び出すたびに、バックエンドの数 - 1 個のゴールーチンがリークします。

## テストを読む

`search/search_test.go`には、`First`関数のテストがあります。
`backend`関数は、指定した時間だけスリープしてから値を返すバックエンドを作ります。
`TestFirst`では、すぐに返す`fast`と、50ミリ秒かかる`slow1`・`slow2`の3つを`First`関数に渡しています。

このテストでは、`First`関数の実行前後でゴールーチン数を比べます。
`runtime.NumGoroutine`関数は、現在存在するゴールーチンの数を返します。

`TODO`コメントに従って、次の処理を実装してください。

1. `First`関数を呼び出す前に、`runtime.NumGoroutine`関数でゴールーチン数を取得する
2. 遅いバックエンドが処理を終えるのに十分な時間（200ミリ秒）待つ
3. 再びゴールーチン数を取得して、`t.Logf`で実行前と実行後の数を表示する

## 動かす

次のコマンドでテストを実行します。
`-v`をつけるとテストのログが表示されます。
このハンズオンでは、データ競合を見逃さないよう、`go test`は常に`-race`をつけて実行します。

```
$ go test -race -v ./...
```

次のように表示されれば成功です。
ゴールーチン数の絶対値は環境によって異なる場合がありますが、実行後のほうが2つ多くなっているはずです。

```
=== RUN   TestFirst
    search_test.go:40: ゴールーチン数: 実行前=2, 実行後=4
--- PASS: TestFirst (0.20s)
PASS
```

`First`関数が終わったあと、遅いバックエンドの処理はすべて終わっているはずなのに、ゴールーチンが2つ残っています。
これがリークしたゴールーチンです。

テストは`PASS`しています。
`got`の値を確認するだけのテストでは、ゴールーチンがリークしていることに気づけません。
このように、ゴールーチンリークは機能のテストが通っていても残り続けるため、見つけにくい不具合です。

## 考えてみよう

* 2つ目以降に返ってきたゴールーチンはどうなるか
* `go test ./...`が成功するのに、リークしているのはなぜか
* `NumGoroutine`の数を比べる方法は、リークの検出にどのくらい使えるか（ほかのゴールーチンが増減するとどうなるか）

## トラブルシューティング

### ゴールーチン数が増えていない

遅いバックエンドの処理が終わる前にゴールーチン数を取得している可能性があります。
バックエンドは50ミリ秒かかるので、`First`関数を呼び出したあとに、それより長く待ってから`runtime.NumGoroutine`関数を呼び出してください。

### Goのバージョンに関するエラーが出る

`go.mod`の`go`ディレクティブはGo 1.27.1です。
`go version`コマンドでインストールされているバージョンを確認してください。
Go 1.21以上であれば、`go`コマンドが必要なツールチェーンを自動でダウンロードします。
